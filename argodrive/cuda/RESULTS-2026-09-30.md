# CUDA SSD-streaming results, 2026-09-30

Box: one RTX PRO 6000 Blackwell 96 GB (passthrough), Threadripper PRO 9955WX (16 vCPU), 60 GiB VM RAM,
3x WD SN8100 RAID0 (2 MiB chunk) exposed to the VM as one virtio-scsi LV, Samsung 9100 PRO system disk.
Model: DeepSeek V4.1 Flash Q4 (519 GB GGUF, 40 layers, 384 routed experts per layer, 19 MiB per expert).
Serving: `ds4-server --cuda --ssd-streaming --ssd-streaming-cache-experts 4600 --ctx 8192`, one GPU.
Harness: OpenAI-compatible requests; 512-token prompt / 400 generated tokens; prompts fixed per run
(seeds 11-15 or 21-24) so arms compare the same prompts; every arm also runs a temperature-0 request
whose SHA-256 must equal the unmodified build's (81e7ab1fbdfc). Decode = generated tokens / (server time -
prefill time). Same-config spread is about +/-1 tok/s, so anything under 5% needs an A/B/B/A.

## Production stack (all bit-exact)

| Lever | Env | Effect |
|---|---|---|
| Tunable VRAM reserve (was 8 GiB hardcoded) | `DS4_CUDA_VRAM_RESERVE_MB=2048` | +11% decode from the extra slots |
| Context 32768 -> 8192 | `--ctx 8192` | +12% decode (+194 slots) |
| Host-RAM expert pool, miss-ranked preload | `DS4_CUDA_HOST_EXPERT_CACHE_GB=40 DS4_CUDA_HOST_TIER_LOAD=<ranking>` | +23% decode at equal VRAM slots |
| Parallel expert reads (upstream default OFF) | `DS4_CUDA_PARALLEL_EXPERT_READ=1` | +15% prefill |
| Wider staging ring / reader pool | `DS4_CUDA_STAGE_RING=16 DS4_CUDA_EXPERT_READERS=8` | +7% prefill on top |
| Prefill next-layer prefetch OFF (upstream turns it on at >= 2048 tokens) | `DS4_CUDA_DISABLE_SSD_PREFETCH=1` | **+50% prefill at 2.5k tokens** (116/118 -> 176); forcing it on at 512 tokens drops prefill 120 -> 47. Its single-stream reads compete with the demand path; routing its reads through the parallel helper pool made it worse (112). At 2.5k tokens with it off, cold prefill + eviction bias reach 205. |
| Async shared expert (upstream enables the dedicated stream only on DGX Spark) | `DS4_CUDA_SHARED_ASYNC=1` | **+5% decode** (19.3/18.5 vs 18.3/17.8), prefill unchanged |
| Pool-aware eviction + cold prefill | `DS4_CUDA_POOL_EVICT_BIAS=50 DS4_CUDA_PREFILL_COLD=1` | A/B/B/A on the full stack: decode neutral (19.1/20.7 vs 19.6/19.4), **prefill +25% at 512 tokens (120 -> 150) and +16% at 2.5k (176 -> 204)**. Matrix: bias alone 20 -> 19.4, 50 -> 18.7, 100 -> 17.8, 500 -> 17.1 (base 18.0); cold alone 17.3 / 138. Pool-backed VRAM slots age faster so VRAM keeps what the pool cannot serve; prefill fills are demoted so a prompt does not flush the decode working set. |\n| Replica reads from the system SSD (sparse replica of gate+up tensors, 204 GB) | `DS4_CUDA_REPLICAS=/replica/model.gguf*1 DS4_CUDA_PRIMARY_WEIGHT=4` | **+8% decode, +4% prefill** (A/B/B/A: 16.9/17.3 vs 18.0/19.0; prefill 115/117 vs 120/122) |

Replica weights measured (fixed prompts): primary 4 (replica carries 13% of bytes) best; 5 close; 3 and 2
(17-21% of bytes) lose because the virtio-attached Samsung tops out near 5-7 GB/s while the array delivers
~28-30 GB/s at depth. 8 helper threads were not better than 4.

## Measured and rejected (bit-exact unless noted)

| Lever | Result |
|---|---|
| Decode read-ahead (port of Metal `DS4_ARGODRIVE_DECODE_AHEAD`) | prediction 3.9/6 as on Metal, but decode 14.7-18.3 vs 17.6-18.6 controls in every variant (K, MIN_W, skip weak layers, early issue, host-pool-only). The array is bandwidth-saturated during read bursts, so speculative reads are taken from the demand path; even pure-DMA speculation queues ahead of demand uploads. Kept default-off. |
| MOE_Q4_GATE_H16R8 and the other single-token Q4 gate variants | flat (paired 18.1/18.5 vs 19.0/18.1) |
| MOE_DIRECT_MIDQ, DECODE_HEADS8_ONLINE, DECODE_SCORE4/8, EXACT_SCORE_SPLIT_VEC4 | change the output hash; not used |
| Batched expert reads, read coalescing | flat; selected experts are almost never adjacent on disk (merge ratio 1.01) |
| VRAM popularity seeding | flat; LRU's 85% hit rate beats a static ranking's 76.5% |
| Request-ranked pool | worse than miss-ranked (19% vs 22% capture) |
| Pool above 40 GB | worse (VM memory pressure) |
| Flag readback instead of id readback | flat; the wait is the router's completion, not the copy |
| CPU expert compute over 8-channel RAM | 12x slower than the PCIe path |
| Speculative decoding | not available for V4.1 (no DSpark support GGUF) |
| Expert sub-reads (`DS4_CUDA_EXPERT_SUBREADS`) | flat at 2 and 3 parts; per-drive queue depth is not the limit on this virtio array |
| Async upload wait (`DS4_CUDA_ASYNC_UPLOAD_WAIT`) | flat; the DMA time is on the critical path either way |
| Deferred-miss MoE (`DS4_CUDA_MOE_DEFER`) | runs (45% of layers finish in one pass, 0 fallbacks) but A/B/B/A 19.5 vs 22.1: slower, and not bit-reproducible (summation order follows the miss pattern) |
| GPU clock lock (`nvidia-smi -lgc 3090`) | flat |
| VRAM reserve 1024 MB (+55 slots) | flat on 512 and 2.5k prompts |
| Prefill prefetch through the helper pool | worse than off (112 vs 176 at 2.5k) |
| Streaming decode islands (`DS4_CUDA_STREAM_ISLANDS`: CUDA-graph capture of the position-independent kernel runs per layer) | flat (19.4 vs 19.5) and the output hash changes under capture; not promoted |
| Pinned side-stream readback (`DS4_CUDA_SIDE_READBACK`) | flat |
| Attention score-split kernel (`DS4_CUDA_EXACT_SCORE_SPLIT_VEC4`) | slower (18.4 vs 19.5) and changes the hash |
| Replica covering the down tensors too (primary weight 5-7) | within noise (19.9-20.6 vs 20.0/19.4) for 102 GB more disk; reverted |
| Exact 6-way split of the down-projection kernel (`DS4_CUDA_MOE_DOWN_SPLIT6`) | flat (19.6/20.6 vs 20.5/19.9); GPU kernels are a minor term |
| Chunked read-to-DMA pipelining (`DS4_CUDA_EXPERT_CHUNKS` 2/4/8) | negative (17.7/15.9/13.6 vs 19.3/19.9): DMA wait halved but smaller O_DIRECT requests lose array bandwidth; keep 6 MiB component reads |
| GPU-gated all-resident path (`DS4_CUDA_MOE_GATE`, spin-wait kernel on a host flag) | deadlocked in the engine at the first decode layer (host stuck in an upload-stream sync); isolated reproductions pass; dropped, never enable |

## Prefix reuse
The KV disk cache already reuses a shared system prompt across new chats with the default flags: a new chat
sharing a 2,248-token system prompt hit the disk cache in 2 ms and prefilled only its 13 new tokens (0.5-0.8 s
instead of 30.8 s for the first cold chat). `--kv-cache-boundary-align-tokens 256` changed nothing.

## In measurement at the time of writing
Host-pool re-ranking under the new eviction policy (800-token A/B/B/A).

## Measured decode partition (2026-10-01 05:07 UTC, 85,399 decode layers, 800-token generations, production stack)
Per layer: router-id readback (= GPU drain) 0.170 ms; host expert phase 0.822 ms, of which reads + issue 0.612 ms and
DMA wait 0.206 ms; 0.80 misses per layer. Per 40-layer token: readback 6.8 ms, host phase 32.9 ms, against a measured
token of ~45 ms (22 tok/s). The GPU kernels are therefore a minor term; the expert read path (bandwidth-bound at
~33 GB/s per 19 MiB expert over virtio) and the exposed DMA tail are the critical path. Pool-capacity curve from the
real-traffic histogram: 42.1% of misses captured at 2,156 slots (today), 60.4% at 4,096; with a miss at ~0.6 ms vs a pool
hit at ~0.37 ms, a 76 GB pool is worth ~+3%, not the +23% it gave when a miss cost 1.9 ms.

## Where it stands
512-token prompts: decode 17.1 -> ~20-22 (strict metric), prefill 115 -> ~150. 2.5k-token prompts: prefill 116 -> 204.
Server-side per-chunk decode average: ~18 -> 21.8.
